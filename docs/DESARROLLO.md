## 📅 Marco Temporal
El desarrollo práctico del proyecto se llevará a cabo de manera paralela durante el periodo de **Formación en el Centro de Trabajo / Estancia en Empresa (FCT / FFEOE)**.

---

## 🔍 Control de Seguimiento

Durante este periodo no solo se evaluará el resultado final del código, sino **el proceso continuo de desarrollo**. Para demostrar la autoría y el trabajo progresivo, el alumnado debe garantizar la trazabilidad de su proyecto a través de dos mecanismos obligatorios:

### 1. Bitácora de Trabajo
Es un registro semanal en formato tabla donde se reflejarán los avances, las decisiones técnicas adoptadas y las incidencias resueltas. 

* **Ubicación:** Debe mantenerse actualizada dentro del `README.md` de tu repositorio.
* **Frecuencia:** Se debe actualizar al finalizar cada semana de desarrollo. 

#### 📝 Plantilla de la Bitácora

| Semana / Fecha | Tareas Realizadas | Decisiones Técnicas / Cambios | Dificultades o Incidencias |
| :---: | :--- | :--- | :--- |
| **Semana 1** *(DD/MM - DD/MM)* | • Configuración inicial del proyecto y repositorio.<br>• Maquetación de la interfaz y pantallas principales. | Definición de los estilos globales y estructura de vistas. | Dificultades al adaptar el diseño a dispositivos móviles (Resuelto). |
| **Semana 2** *(DD/MM - DD/MM)* | • Creación inicial de la base de datos y sus tablas.<br>• Conexión de la aplicación con la base de datos. | Elección del motor de base de datos para el proyecto. | Fallo de conexión inicial entre la aplicación y la BBDD (Resuelto). |
| **Semana 3** *(DD/MM - DD/MM)* | • Programación de los formularios de registro y consulta de datos.<br>• Integración de la interfaz con la base de datos. | Estructuración del código en módulos y carpetas. | Ninguna. |

---

### 2. Historial de Commits en GitHub
El repositorio debe reflejar la evolución real del proyecto mediante un flujo de trabajo continuo:

* **Frecuencia constante:** Los avances deben subirse periódicamente a GitHub a lo largo de todo el proceso de desarrollo.
* **Commits atómicos:** Cada commit debe responder a una unidad lógica de trabajo (ej. *'feat: añadido endpoint de login'*, *'fix: corrección de validación en formulario'*).
* **Mensajes descriptivos:** Se deben evitar mensajes genéricos o vacíos de contenido (*'cambios'*, *'arreglo'*, *'f2'*, etc.).
